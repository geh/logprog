# Motivation: Why SMT?

SAT solvers reason about propositional formulas. For software verification, however, we often need to reason about higher-level concepts such as equality, arithmetic, and data structures.

One approach is to encode a program and its assertions as propositional formulas and ask a SAT solver whether a counterexample exists. This encoding can lose high-level information and may require many clauses to represent simple arithmetic operations. For example, a contradiction such as `a == 1` together with `assert(a != 1)` is easy to recognize at the source level, but its propositional encoding may be much less transparent.

**Satisfiability Modulo Theories (SMT)** addresses this problem by combining Boolean reasoning with specialized theories, such as arithmetic, arrays, and bit-vectors. This lets a solver reason about the structure of the problem instead of representing everything directly in propositional logic.

## Satisfiability Modulo Theories (SMT)

  * Some problems are better expressed in languages other than propositional logic.
  * For example, software verification requires reasoning about *equality*, *arithmetic*, *data structures*, and so on.

  * SMT decides the satisfiability of a quantifier-free first-order formula with respect to a background theory.
  * *First-order logic* is richer than propositional logic, but harder to automate.
  * A *background theory* is a set of formulas (axioms) assumed to be true.

  * Example: equality with uninterpreted functions:
  * `$g(a) = c AND (f(g(a)) != f(c) OR g(a) = d) AND c != d`

## Applications

  * Hardware and software verification.
  * Useful theories include uninterpreted functions, arrays, bit-vectors, and combinations of these theories.

## The Lazy Approach to SMT

Example using uninterpreted functions:

`g(a) = c AND (f(g(a)) != f(c) OR g(a) = d) AND c != d`

* Send $\{1,-2 \vee 3, -4\}$ a *SAT solver*
  * *SAT solver*: "SAT with model $[1,-2,-4]$"
  * *Theory solver*: "T-inconsistent"

* Send $\{1,-2 \vee 3, -4, \color{red} -1 \vee 2 \vee 4 \color{black} \}$
  * *SAT solver*: "SAT with model $[1,2,3,-4]$"
  * *Theory solver*: "T-inconsistent"

* Send $\{1,-2 \vee 3, -4, -1 \vee 2 \vee 4, \color{red} -1 \vee -2 \vee -3 \vee 4 \color{black} \}$
  * *SAT solver*: "UNSAT"

## Why Is It Called "Lazy"?

* Theory information is used lazily when checking the T-consistency of propositional models (that is, after the problem has initially been encoded as SAT).
* Characteristics:
  * Advantage: modular and flexible.
  * Disadvantage: theory information does not guide the search.
* The first SMT solvers worked this way (around 2002).

## Optimizations

* ~~Verificar T-consistencia solamente de modelos proposicionales completos~~
* Verificar T-consistencia de interpretaciones parciales que se estan construyendo

* ~~Dado un modelo $M$, agregar $\neg M$ como clause nueva~~
* Dado un modelo $M$, identificar un subconjunto $M_0 \subseteq M$ T-inconsistent, y
  agregar $\neg M_0$ como clause nueva

* ~~When T-inconsistency is found, add a clause and start over.~~
* When T-inconsistency is found, analyze the conflict and backjump.

## Key Points

Advantages of the lazy approach:

  * Each component focuses on its specialty. 
    * \color{blue}SAT solver \color{black} se encarga de la informacion Booleana
    * \color{red}Theory solver \color{black} se encarga de la informacion de su teoria

  * The theory solver receives only conjunctions of literals.

  * Modular approach:
    * The SAT solver and theory solver communicate through a simple API.
    * Supporting a new theory in SMT requires only a new theory solver.
    * A standard SAT solver can be adapted into a lazy SMT system with only a few lines of code.

## Theory Propagation

* The lazy approach has one disadvantage:
  * theory information does not guide the search.

* como mejorar eso? \color{red}theory propagation \color{black}
  *  $M \mid\mid F \Rightarrow  M ~ l \mid\mid F  \text{ si } \begin{cases}M \models_T l \\ l \text{ o } \neg l \text{ ocurre en $F$, no en $M$}\end{cases}$

* The theory solver guides the search by finding theory consequences, rather than merely validating the search as in the lazy approach.

* naive implementation: add $\neg l$. if T-inconsistent, infer $l$.
  Pero para un T-propagate eficiente necesitamos T-solvers especializados

* This approach is called DPLL(T).

## Example

`g(a) = c AND (f(g(a)) != f(c) OR g(a) = d) AND c != d`

* $~ ~ ~ ~ \emptyset \mid\mid 1, -2 \vee 3, -4 \Rightarrow \text{ (Unit Propagate) }$
* $~ ~ ~ ~ 1 \mid\mid -2 \vee 3, -4 \Rightarrow \text{ (T-propagate) }$
* $~ ~ 1 2 \mid\mid 3, -4 \Rightarrow \text{ (Unit Propagate) }$
* $~ 1 2 3 \mid\mid -4 \Rightarrow \text{ (T-Propagate) }$
* $1 2 3 4\mid\mid -4 \Rightarrow \text{ (UNSAT) }$

No *split* operation is used.

## DPLL(T) - Propagation

* Three operations:
  * Unit propagation (SAT solver).
  * Consistency checking (theory solver).
  * Theory propagation (theory solver).
* Cheap operations are performed first.
* If the theory is expensive to check, the theory solver may not be called every time:
  * it may be called only when necessary at the leaves, when a complete propositional model is available.
  * Removing theory propagation does not make the algorithm incorrect.

## DPLL(T) API

What does DPLL(T) require from the theory solver?

* Check the T-consistency of a set of literals `M`, including:
  * Explaining T-inconsistency by finding a small inconsistent subset of `M`.
  * Incrementality: when `l` is added to `M`, checking `M AND l` should be faster than starting from scratch.
* Theory propagation: find the theory consequences of `M`, including an explanation for propagating `l` by finding a small subset of `M` that implies `l`.
* Backtracking: undo the last `n` literals that were added.

## Theory Example: Fixed-size bit vectors

* Represent integers, longs, and similar types.
* Arithmetic operations (`+`, `-`, `*`, `/`, etc.).
* Bitwise operations (`&`, `|`, `^`, etc.).
* Comparisons (`<`, `>`, etc.).
* Decidable, NP complete

## Theory Example: Linear Arithmetic

* Constants, integers, multiplication by an integer constant, addition, subtraction, equality, and greater-than.
* NP-complete over integers.
* Linear arithmetic over the reals is decidable in polynomial time.

## Theory Example: Arrays

* Provides two functions, `read` and `write`.
* Axioms:
    * $\forall a, i, v . read(write(a,i,v),i) = v$
    * $\forall a,i,j,v. i\neq j \rightarrow read(write(a,i,v),j) = read(a,j)$
    * $\forall i, a, b . read(a,i) = read(b,i) \rightarrow a=b$
* NP complete

## Combinations of Theories

* Each theory discussed is decidable on its own, but combinations of theories are not automatically decidable.
* Under certain conditions, theories can be combined using a simple method (Nelson-Oppen):
  1. They share no symbols other than equality (`=`).
  2. They are *stably infinite*.
  3. They are quantifier-free.
* The theories discussed here satisfy these conditions, so they can be combined.
* [More details on Nelson-Oppen](https://excape.cis.upenn.edu/documents/ClarkBarrettSlides.pdf)

## SMT-LIB 2: Writing SMT Problems

SMT solvers accept logical formulas expressed in a language such as SMT-LIB 2. An SMT-LIB script declares variables, asserts constraints, and asks the solver to check satisfiability.

A typical script follows this structure:

```lisp
(set-option :produce-models true)
(set-logic QF_LIA)

(declare-const x Int)
(declare-const y Int)

(assert (> x 0))
(assert (= (+ x y) 10))

(check-sat)
(get-model)
```

The commands have the following roles:

- `set-option` configures the solver. Here, it requests that a model be available when the problem is satisfiable.
- `set-logic` identifies the logical fragment being used.
- `declare-const` declares a constant of a specified sort (type).
- `assert` adds a constraint to the problem.
- `check-sat` asks whether all asserted constraints can hold simultaneously.
- `get-model` requests a satisfying interpretation of the declared constants and functions.

In this example, the solver can return `sat` and a model assigning values to `x` and `y` that satisfy both constraints. There may be multiple valid models.

If the constraints are inconsistent, the solver returns `unsat`. A solver may also return `unknown` when it cannot determine satisfiability.

### Expression syntax

SMT-LIB uses prefix notation: the operator appears before its arguments.

For example, the arithmetic expression

\[
x + 3 \leq 2y
\]

is written as:

```lisp
(assert (<= (+ x 3) (* 2 y)))
```

Boolean operators and arithmetic expressions can be nested:

```lisp
(assert
  (and
    (> x 0)
    (or (< y 5) (= y 10))))
```

The `ite` operator expresses a conditional expression. The expression `(ite c a b)` evaluates to `a` when Boolean condition `c` holds, and to `b` otherwise. The two branches must have the same sort.

For example:

```lisp
(declare-const x Int)

(assert (= (ite (> x 0) x (- x)) 5))
(check-sat)
```

This constraint requires the absolute value of `x` to be 5.

A semicolon (`;`) begins a comment that continues to the end of the line.

### Arithmetic theories

The `set-logic` command can identify a fragment of first-order logic supported by the solver. Some common arithmetic fragments are:

| Logic | Meaning |
|---|---|
| `QF_LIA` | Quantifier-free linear integer arithmetic |
| `QF_LRA` | Quantifier-free linear real arithmetic |
| `QF_IDL` | Quantifier-free integer difference logic |
| `QF_RDL` | Quantifier-free real difference logic |

**Quantifier-free** means that formulas do not contain universal or existential quantifiers. **Linear arithmetic** permits linear expressions over integers or reals, rather than unrestricted multiplication of variables. **Difference logic** restricts arithmetic constraints to forms based on differences between variables and constants.

For example, the following constraints belong to linear integer arithmetic:

```lisp
(set-logic QF_LIA)

(declare-const x Int)
(declare-const y Int)

(assert (= (+ x y) 10))
(assert (= (+ x (* 2 y)) 20))

(check-sat)
(get-model)
```

The solver finds `x = 0` and `y = 10`.

The choice of logic communicates the intended fragment to the solver and can help it select appropriate solving techniques. Use a logic compatible with the operations and sorts in your problem.
